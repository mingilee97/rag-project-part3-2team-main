### 1 프로젝트 목표와 최종 선택

이 프로젝트는 HWP와 PDF 제안요청서 100건에서 질문과 관련된 근거를 찾아 한국어 답변을 만드는 RAG 시스템이다. 긴 문서의 요구사항과 조건을 사람이 일일이 찾는 부담을 줄이는 것이 목표다.

현재 실행 구성은 FINAL-02 하나로 정리했다. 10월 19일 실험 기록의 채택 제안 이후, 사용자가 10월 20일 제공한 재현 코드를 최종본으로 선택했다. 이전 구현과 평가의 출처는 문서와 Git 이력에 보존한다.

FINAL-02는 FINAL-01보다 문맥과 기록된 검색 시간이 작고 질문 분해 호출이 추가되지 않는다. 답변 점수의 작은 차이는 통계적으로 유의하지 않다고 기록돼 있어, 정확도가 더 높다고 단정하는 대신 실행의 단순성과 입력 부담을 고려해 선택했다.

| 단계 | FINAL-02 설정 |

## 2 실행 구조와 모듈화

문서 준비와 질문 처리를 나눴다. 문서 준비는 파싱 캐시와 메타데이터를 연결하고 청크를 만든다. 질문이 들어오면 사업을 식별하고 검색 후보를 합쳐 재순위화한 뒤 상위 근거를 생성 모델에 전달한다.

문서와 파싱 캐시 → 청킹과 임베딩 → 사업 식별과 검색 → RRF와 재순위화 → 근거 6개와 답변 → 검색과 답변 평가

| 모듈 | 역할 |
| --- | --- |
| config.py | 최종 모델·문서 선택·청킹·검색 설정 |
| parsing.py | HWP/PDF 추출과 성공·실패 캐시 |
| data.py | 평가셋 1.1 검증, 메타데이터 연결과 말뭉치 준비 |
| chunking.py | 헤더 없는 문서 분할과 청크 번호 부여 |
| embedding.py | 원본 BGE 임베딩 모델 연결 |
| routing.py | 사업명·별칭·기관을 이용한 사업 식별 |
| retrieval.py | 사업 범위별 FAISS·Kiwi BM25와 RRF 결합 |
| reranking.py | 검색 후보 전체를 BGE로 다시 정렬 |
| generation.py와 pipeline.py | 원본 프롬프트·생성 연결·답변 캐시·출처 기록 |
| metrics.py와 evaluation.py | 근거 문장 순위·포함률과 Gemini 채점 |
| experiments.py | base·ragas·summary, 문항별 체크포인트 |
| __main__.py | ask·평가·오프라인 검사 명령 |

각 모듈은 rfp_rag 아래에 있다. 사업을 찾지 못하거나 모호하면 전체 문서에서 검색하는 원본 동작을 유지했다. 질문 분해·청크 사업명 헤더·숫자 후처리를 새로운 기능처럼 추가하지 않았다.

원본 설정 파일에는 10문서·700/100·GTE가 남아 있었으나 final02.py가 이를 덮어썼다. 새 기본값은 실제 FINAL-02 실행 설정과 맞췄고, 프롬프트는 원본 파일의 바이트를 그대로 보존했다.

### 청킹과 검색에서 배운 점

작은 실험에서는 700/100에서 1000/200으로 청크를 넓히며 필요한 근거를 한 조각에 더 담는 방향을 확인했다. 다만 맞는 청크 하나를 찾는 것과 여러 절에 흩어진 근거를 모두 모으는 것은 다른 문제였다.

리랭커나 청크 크기로 검색 순위가 좋아져도 생성 지표가 같은 폭으로 좋아지지는 않았다. 이 때문에 검색 성과와 답변 성과를 분리하고, 질문 유형별 근거 누락도 함께 보았다.

### 과거 코드의 보존

구버전 실행 폴더와 선택기는 현재 기본 실행에서 제거했다. 당시 README·출처·평가 해석·설정 기록은 docs/history에 보존했다. 교체 전 전체 코드는 Git commit 0f77930191bcb5d5b12c13a8d52d08184154c2f6에서 확인할 수 있다. Git 이력과 별도 modular 저장소는 변경하지 않았다.

제공된 all_scores.csv 300행을 읽어 평균을 다시 계산했고 five_metric_summary.csv와 같은 값을 확인했다. 문항별 질문·답변·문맥·채점 이유는 공개하지 않고 숫자 집계만 보존한다.

| MRR | 0.8618 | 289문항, 첫 근거 순위의 역수 평균 |

Faithfulness가 높아도 질문에 필요한 사실을 모두 답했다는 뜻은 아니다. 이번 결과에서도 F1과 근거 전부 전달 비율을 함께 봐야 한다. 원본 계산은 텍스트 정규화 후 근거 문장 포함 여부를 사용하므로 의미가 같은 표현을 모두 판별하는 평가가 아니다.

FINAL-02의 문맥은 약 27% 짧고 기록된 검색 중앙값도 작다. 질문 분해용 추가 호출이 없고 실행 구성이 단순하다는 점을 고려해 최종 실행으로 선택했다. 여러 절 질문의 근거 확보에는 FINAL-01의 강점이 남으므로 선택이 모든 질문 유형의 우월성을 뜻하지 않는다.

Hit@5와 MRR은 두 후보의 순위 단위가 parent와 일반 청크로 다르다. 이를 나란히 놓고 검색 성능의 승패를 정하지 않는다. 다른 장비·최초 구축·동시 부하가 섞인 속도 비교로 확대하지 않으며, 비용 절감률도 새 실측 없이 제시하지 않는다.

## 6 재현에 필요한 자료와 실행

정확한 재현에는 원본 문서 100건, 함께 제공된 파싱 캐시, data_list.csv, 평가셋 dev_benchmark_v1.1.json이 필요하다. 이 자료는 원문과 질문·답변을 담을 수 있어 공개 저장소에서 제외했다. 승인된 비공개 보관본을 별도로 준비해야 한다.

```sh
python -m pip install -r requirements.txt
python -m pip install --no-deps langchain-hwp-hwpx-loader==0.1.1
python -m rfp_rag ask --query "이 사업의 요구사항을 설명해 줘."
python final02.py base --limit 3 --out-dir results/FINAL-02-test
python final02.py base
python final02.py ragas
python final02.py summary
```

ask와 base는 임베딩·리랭커를 로드하고 Claude를 호출할 수 있다. base의 Judge와 ragas는 Gemini를 호출한다. 위 명령은 재현 안내이며 이번 정리에서 실행하지 않았다. 설치·다운로드와 예상 호출량·예산을 확인한 뒤 실행해야 한다.

FINAL-02는 VM의 파싱 캐시를 기준으로 한다. Colab의 다른 캐시와 다섯 문서에서 본문 길이가 다르다고 제공 가이드가 명시한다. 같은 파일명이라도 본문이 다르면 청크와 검색 결과가 달라진다. 비공개 자료의 해시를 source-manifest.json에 기록해 같은 사본인지 비교할 수 있게 했다.

원본의 문항별 체크포인트, 다른 설정의 결과 폴더 재사용 차단, RAGAS 호출마다 Gemini 클라이언트를 만드는 동작을 유지했다. 결과 폴더와 .env는 Git에서 제외한다. 키 일부를 출력하던 구문은 제거했다.

모델 로더의 trust_remote_code 설정은 원본과 같다. 모델 revision과 제공 코드를 검토하기 전에는 자동 다운로드나 실행을 하지 않는다. GPU·새 설치 환경·외부 API의 실제 호환성은 이번 오프라인 검증으로 확인되지 않았다.
