## 기존 비교를 해석하는 조건

10월8일 교정 결과는 같은 168질문을 썼지만 BM25는 100문서, KURE는 정답 문서 ID로 고른 14문서만 검색했다. 86개 방해 문서가 빠진 KURE의 절대값을 BM25와 직접 비교할 수 없다. 각 검색 방식 안에서 메인과 후보 청킹을 비교한다.

전체 인용 구간 508개 중 원문에서 찾을 수 있는 것은 491개다. 원문에 없는 17개를 검색 실패로만 부르면 데이터 한계가 섞인다. 168질문은 14사업에 묶여 있어 독립 표본 168개로 해석하지 않는다. 문항 완전 회수 지표에는 원문 인용이 하나도 없는 16문항을 별도 제외한다. 따옴표 안의 긴 인용, 생략 구간 제외, 정답 문서의 본문만 인정하는 교정 evaluator를 사용했다.

과거 기록의 `exact_cosine`은 실제로 BF16에서 정규화한 뒤 float32로 저장한 벡터의 dot 전수 검색이었다. 기존14문서 벡터의 최대 단위 정규화 오차는 약0.3785%였고, float32로 다시 정규화하면 top5 집합이 메인15/168질문·후보18/168질문에서 달라졌다. 따라서 정밀도에 무관한 순위라고 주장하지 않는다. 원래 벡터·순위·과거 결과는 보존했고, 새 설명에는 '정규화 임베딩의 dot 전수 검색(BF16 정규화 오차 포함)'을 사용한다. 이 별도 진단은 기존14문서 범위이며 전체100문서의 점수 변화나 생성 정확도를 측정한 결과가 아니다.

| 실제 측정 | 메인 | 후보 | 해석 |
|---|---:|---:|---|
| 100문서 BM25, top5 인용 회수 | 296/491 | child 206/491 | child가 짧아 근거를 덜 담음 |
| 14문서 KURE, top5 인용 회수 | 345/491 | child 273/491 | 방해 문서 없는 부품 비교에서 메인 우세 |
| 14문서 KURE, 4,000토큰 parent 확장 | child 273/491 | parent 286/491 | 인용 총량은 늘지만 any-hit 문항 115→111, 완전 문항 81→87로 혼합 효과 |

4,000토큰은 cached `o200k_base`로 센 근거 예산이다. EXAONE tokenizer와 system·질문·출력 예약까지 포함한 전체 프롬프트 적합성의 증거가 아니다. BGE logit을 코사인 0.45 gate에 그대로 넣으면 척도가 달라 호환되지 않는다.

## BGE 실제 CPU pilot

첫 네 사업의 첫 질문4개를 결과를 보기 전에 고정했다. 같은 14문서·KURE 벡터·pool20·body-only BGE·4,000 o200k 근거 예산에서 실행했다. BGE 160쌍, CPU4스레드 BF16, max_length1024, 총 61.57초였다. 새로운 임베딩·생성·judge·GPU·유료·다운로드 호출은 없었다.

| 처리 | 원문 인용 회수 | any-hit/완전 문항 | 평균 근거 토큰 |
|---|---:|---:|---:|
| main dense top5 | 11/11 | 4/4 · 4/4 | 2,406.75 |
| main BGE top5 | 11/11 | 4/4 · 4/4 | 2,813.25 |
| child dense top5 | 6/11 | 3/4 · 3/4 | 1,301.00 |
| child BGE top5 | 11/11 | 4/4 · 4/4 | 1,996.50 |
| parent dense pool20 | 6/11 | 3/4 · 3/4 | 2,241.00 |
| parent BGE pool20 | 11/11 | 4/4 · 4/4 | 2,847.25 |

짧은 child의 회수 손실을 BGE가 줄인 이 네 문항의 사례를 확인했다. 메인보다 전체 품질이 좋다는 결론은 이 표에서 나오지 않는다. 비용은 실제 CPU 시간과 추가 pair 수로 보고하며 유료 API 가격을 0원 절감했다고 주장하지 않는다.

## 전체 평가와 선정 조건

100문서 전체의 같은 168질문 비교를 새 체크포인트로 실행 중이다. 기존 14문서의 같은 텍스트 벡터를 해시·순서 확인 후 재사용하고, 나머지 86문서를 양쪽에 모두 임베딩한다. 검색 부품 6처리와 동일 CPU EXAONE의 답변/규칙 검증 3처리를 구분한다. CPU 생성은 메인의 answer/verify 로직을 사용하지만 route·CSV·summary·코사인 gate를 포함한 등록 전체 파이프라인 평가와 같지 않다.

실제 생성 pilot은 4질문×3처리=12입력 모두 성공했고 오류0, 관측 VRAM0이었다. 평균 지연은 main34.58초, BGE child33.03초, BGE parent42.78초다. 규칙 검증 뒤 근거에 없는 확인 대상 숫자·날짜의 검출은0이었지만 같은 규칙으로 수정한 답을 확인한 결과이므로 독립 정확도 평가가 아니다. semantic judge는 호출하지 않았다. [생성 집계](../evaluation/aggregates/20261009-generation-pilot.json)에 조건과 한계를 보관했다. 전체504입력 생성은 약5.15시간이라는 갱신 추정에 따라 첫 입력 전에 보류했으며 자동으로 시작하지 않는다.

Windows에서 기존 실행기는 GPU 50% 제한을 보장하지 못해 등록 평가를 VM으로 제한한다. 이를 삭제하거나 등록 인자를 빼지 않았다. [Ollama 공식 API](https://docs.ollama.com/api/chat)와 [옵션 정의](https://github.com/ollama/ollama/blob/main/api/types.go)의 `num_gpu=0,num_thread=4`를 별도 CPU 클라이언트로 전달하고, 실제 `/api/ps`에서 `size_vram=0`을 확인한다. 설치된 client는 0.35.1이며 공식 main 소스의 버전과 혼동하지 않는다.

로컬에서 어려운 설정은 VM 또는 Colab을 사용하라는 최신 요청에 따라 [최소 실행 준비](../evaluation/VM-COLAB.md), 모델 호출 없는 [사전 점검](../evaluation/vm-preflight.py), Linux 전용 GPU transport와 별도 evaluator를 추가했다. CPU 생성 코드와 Windows 가드는 보존한다. 같은 EXAONE GGUF Q4_K_M의 digest·Ollama 버전·prompt 설정을 고정하며 생성 뒤 실제 GPU 적재를 요구한다. 코드 준비와 실제 VM 모델 실행은 구분하고 GPU 사용률50% 제한을 보장했다고 표시하지 않는다.

새 후보의 채택에는 동일 corpus·질문·생성 설정·예산·분모, 검색의 any-hit/완전 회수·회귀 문항, 답변 정확도·인용 적합성·거절 정확도, 지연시간·메모리·추가 호출 비용이 필요하다. 독립 semantic judge와 메인 holdout 전체 평가가 없으면 최종 품질 우승은 보류한다. 오류와 누락은 `error` 또는 `null`로 기록한다.
